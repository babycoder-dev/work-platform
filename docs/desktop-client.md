# 客户端架构取舍

## 1. 结论

客户端分成两条线：

```text
Web UI
  面向所有用户
  覆盖 Windows 7 兼容模式
  承载完整功能与管理能力

Native C/S Client
  面向 Windows 10+/Windows 11 与 Linux
  追求高性能、低内存、低配机器体验
  承载高频操作
```

明确取舍：

- 不为 Windows 7 做原生 C/S 客户端。
- 不用旧版 Electron、旧版 Qt、旧版 WebView2 绑定整个客户端技术路线。
- Windows 7 用户通过 Web UI 访问核心功能。
- 原生客户端使用现代受支持技术栈，优先性能与长期维护。

## 2. 为什么这样取舍

如果强行要求原生 C/S 客户端兼容 Windows 7，会导致：

- 技术栈必须停留在旧版本。
- 安全更新和运行时维护风险上升。
- UI、打包、网络库、浏览器内核都会受旧系统约束。
- 后续 IM、多维表格等高交互能力会被拖慢。

把 Windows 7 降级为 Web UI 兼容目标，可以让：

- C/S 客户端使用 Qt 6.8 LTS 等现代技术。
- 桌面端性能、启动速度、内存占用更可控。
- Web UI 保持覆盖面。
- 项目整体维护成本更合理。

## 3. 原生 C/S 客户端

默认技术：Qt 6.8 LTS C++。

目标平台：

- Windows 10 1809+ x64
- Windows 11 x64
- Ubuntu x64，后续阶段

技术原则：

- 优先 Qt Widgets。
- 复杂图形或动效再评估 Qt Quick。
- 不使用 WebView 作为主界面。
- 所有网络请求异步执行。
- 不直接连接数据库。
- 只通过 `gateway-api` 与公开 API 契约访问后端。

首期功能：

- 服务地址配置
- 内部账号登录
- 当前用户信息
- 在位看板
- 状态登记
- 通知提醒占位

后续功能：

- 审批待办
- 审批处理
- 日/周报填写
- 常用通知

复杂管理能力优先放在 Web UI。

## 4. 性能基线

已确认的首期性能基线：

- Windows 10 低配机器冷启动目标：2 秒内进入登录页。
- 常驻内存目标：空闲小于 120 MB。
- 在位看板目标：1000 人以内列表滚动和筛选无明显卡顿。
- 请求、解析、文件读写不得阻塞 UI 线程。
- 大列表必须使用分页、增量加载或模型视图懒加载。

## 5. Windows 7 Web UI 兼容模式

Windows 7 只支持 Web UI，不支持原生 C/S 客户端。

兼容浏览器目标：

```text
Chrome 109
Edge 109
Firefox 115 ESR
```

兼容范围：

- 登录
- 首页导航
- 在位看板
- 状态登记
- 审批待办
- 日/周报填写

可降级范围：

- 复杂动效
- 大规模实时刷新
- 多维表格高级编辑体验
- IM 高级能力

Web UI 要求：

- 静态资源全部内网部署。
- 不使用公网 CDN、外部字体、外部脚本。
- 构建时提供 legacy target。
- 避免强依赖现代浏览器独有 API。

## 6. 本地数据

C/S 客户端本地只保存必要数据：

- 服务地址
- 登录 token 或会话信息
- 用户偏好
- 草稿数据，可选

默认不做完整离线同步。若需要离线草稿，优先使用 SQLite。

## 7. 发布

Windows：

- Qt 6.8 LTS
- MSVC 2022 或 MinGW-w64
- 安装包可选 NSIS、Qt Installer Framework 或 MSI
- 只支持 64 位安装包

Linux：

- Qt 6.8 LTS
- GCC
- 安装包可选 AppImage、deb、rpm
- 初期只预留 Ubuntu x64，首期版本不作为主要交付目标

内网发布：

- 安装包放入内部文件服务器或制品库。
- 自动更新如需实现，必须使用内网更新源。
