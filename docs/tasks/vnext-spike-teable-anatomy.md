# 任务包：vNext spike —— Teable 解剖（M17-M18 前置）

状态：Ready（**前置**：`docs/adr/0006-vnext-roadmap.md` 与 `docs/research/README.md`
随文档落地计划 Task 1/6 入库后方可开工）｜ 类型：研究型 spike（产出报告，不改产品代码）｜
依据 `docs/adr/0006-vnext-roadmap.md`（设计推演见
`docs/superpowers/specs/2026-07-05-vnext-roadmap-design.md` §3.1/§10/§11）；报告规范见
`docs/research/README.md`。

## 1. 目标

为 **bitable 存储模型子 ADR** 与 **M17（数据引擎）/M18（表格 UI）RFC** 产出量化的
**可搬运清单 / 需自研清单 / 风险清单**。spec 已定调"动态物理表（Teable 路线）+ 解剖后
成块搬运"，本 spike 把"成块搬运"从口号变成带源码路径与缝合点预估的清单；若发现动态
物理表路线的重大反证，如实报告（翻案须新 ADR）。

## 2. 范围

**做**：

1. **跑起来 + 黑盒观察动态 DDL**：compose 起 Teable CE（锁定版本/commit），实操建 base/
   表/字段（覆盖全部字段类型）/视图/公式/关联；同时开 `psql` 观察 PG 侧行为——用户表的
   物理表名与列名策略、字段增删改对应的 DDL 语句、索引策略、行删除语义、关联字段的物理
   实现（外键？中间表？）、undo/历史的存储位置。**这是报告最值钱的一章，逐操作记录
   "UI 动作 → SQL/DDL"对照。**
2. **源码解剖（路径级结论）**，五个子系统：
   - **DDL 管理层**：动态建表/改列的入口、事务与失败回滚、命名与配额约束——M17 自研
     DDL 管理层的直接参照；
   - **字段类型系统**：类型定义/校验/单元格值转换的代码组织，估算"抽出来接 Drizzle/我们
     的 API 面"的缝合成本；
   - **公式引擎**：解析器、依赖图构建、增量重算触发——判定"整块搬"还是"只搬解析器"；
   - **视图 = 查询编译**：filter/sort/group 从视图配置到 SQL 的编译路径；
   - **实时协同**：确认机制（ShareDB/OT？自研 CRDT？版本号乐观锁？）与后端承载（room
     server？），并与 **APITable room-server** 的 OT 方案做一节对比——这是 M18"协同方案
     定型"的唯一输入，spec 明说协同机制"spike 中定候选"。
3. **许可分层核实**：apps（AGPL）/ packages（MIT）逐目录确认；企业版特性边界实证
   （automation、权限矩阵、AI 确不在 CE 代码里——找 feature flag 或 EE 目录证据），避免
   "以为能搬结果在闭源里"。
4. **缝合成本评估**（自研清单的另一半）：
   - Prisma → Drizzle：Teable 数据访问层对 Prisma 的耦合深度，元数据表（表/字段/视图定义）
     schema 可否直接翻译；
   - Next.js 网格前端 → 我们的 Vite/React SPA：grid 组件（canvas 渲染/虚拟滚动）对 Next
     的耦合面，能否抽成独立包挂进 `modules/bitable/web`；
   - 权限桥：Teable 的空间/协作者模型在哪些层渗入读写路径——我们换成平台 RBAC/数据
     范围要切断哪些假设（自研面）；
   - 审计接入点、我们的槽位兼容层（forms 迁移）在其 API 面上的落点。
5. **资源基线**：CE compose 全套的内存/磁盘占用（容量规划输入，权重低于 OpenIM/LLM 两
   个 spike）。

**不做**：不 fork、不改 Teable 代码、不做性能极限压测（引用官方"百万行"声明并小规模
抽查即可）、不评估 Teable 云服务、不做 UI 像素对比（M18 设计稿另走设计流程）。

## 3. 执行步骤

1. compose 起 CE，完成 §2.1 黑盒观察（约 30% 时间盒）。
2. §2.2 五子系统源码解剖（约 40%）＋ §2.3 许可核实。
3. §2.4 缝合评估（约 20%）＋ §2.5 资源基线。
4. 报告 `docs/research/teable-anatomy.md`（README 七章规范；"UI 动作 → DDL"对照表与
   搬运/自研清单为核心章）。

## 4. 产出与验收断言

- [ ] "UI 动作 → SQL/DDL"对照记录覆盖：建表、每类字段增删改、**索引策略观察**（字段/
      视图创建时自动生成了什么索引——Teable 索引为自动管理，无"建索引"用户操作）、
      关联字段、行删除。
- [ ] 五个子系统各有路径级结论（目录/文件层面，非"大概在某处"）。
- [ ] **可搬运清单**：每项带源码路径 + 目标落点（我们哪个包/模块）+ 缝合点预估
      （Prisma/Next 解耦工作量的定性分档：低/中/高）。
- [ ] **需自研清单**：至少覆盖权限桥、审计接入、槽位兼容层，并写明 Teable 侧"切断假设"
      的位置。
- [ ] 许可分层核实表（目录 → 许可证）+ 企业版边界证据。
- [ ] 协同机制结论 + 与 APITable OT 方案的对比一节（M18 定型输入）；若对比结论倾向搬运
      APITable 协同代码，报告须提示后续流程义务（product-requirements §5.4 口径须先显式
      翻案）。
- [ ] 报告产出后登记回 `docs/research/README.md` spike 表（状态改「已产出」）。
- [ ] 对 M17 RFC 的决策建议章：DDL 管理层设计要点、元数据 schema 翻译建议、若有动态
      物理表路线的反证在此如实列出。

## 5. 风险与时间盒

- 时间盒：**5 个工作日等效**；五子系统若超盒，按 DDL 管理层 > 字段类型 > 视图编译 >
  公式 > 协同 的优先级裁剪**深度**，被裁项列 open questions。**例外**：协同的机制结论
  （OT/CRDT/版本号是什么 + 与 APITable 对比的定性结论）不可裁——它是 M18 定型唯一输入；
  若深度被裁到只剩结论，须同时在 open questions 登记一个显式的补做 spike 后续任务（M18
  前执行）。
- Teable 迭代快：全部结论带 commit 锚点；M17 启动时若相隔超一个季度，做一次 diff 刷新
  （报告写明保鲜期）。
- AGPL 合规姿态已由 ADR-0006 拍板（纯内部使用），本 spike 不再重议，只核实分层事实。
