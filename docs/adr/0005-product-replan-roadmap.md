# ADR 0005: 产品重规划与梯队路线图

## 状态

Accepted

本 ADR **修正** ADR-0002《基建优先的平台推进策略》中“执行顺序”一节的 M5–M8 安排。
ADR-0002 的核心原则（基建优先、Platform Core 为共享事实源、schema 隔离、桌面端不复制业务规则、
OpenIM 仅作 Provider）**继续有效**；本 ADR 只重排并重定义 M5 之后的里程碑内容。

## 背景

M1–M4 已完成：平台核心（认证、PostgreSQL 持久化、权限/菜单/审计、数据范围解析、Web Shell、
phantom-token 跨进程鉴权）与第一个业务模块（在位 MVP）落地，证明平台能承载业务模块。

进入 M5 前，产品负责人对完整业务需求做了一轮结构化澄清（2026-05），结论与早期“审批优先”的
假设有实质差异。澄清后的完整需求见 `docs/product-requirements.md`。关键发现：

- 真实核心诉求是“**以人为中心的组织管理**”：角色/数据权限、人员档案、在位状态、日报，
  外加随后的审批。早期把“审批”当作 M5 的中心并不匹配实际优先级。
- 多处需求指向同一批**未被显性命名的基建**：**数据权限按数据类型授权的角色管理 UI**、
  **动态表单/自定义字段**、**自研站内通知**、**定时任务调度**、**文件存储**。
- 需求里出现的“即时通讯”经澄清后**本期不需要**——所有诉求用“站内通知 + 近况记录（CRM 式日志）”
  即可满足；人对人聊天移出本期。
- “自定义表单、可配置通知、可配置审批”三者最终都在向“**低代码自动化平台（类飞书多维表格）**”
  收敛，但现在直接建该平台属过早通用化。

## 决策

### 1. 重排里程碑（M5 起重定义；老 M5–M8 作废）

```text
M5  权限与角色管理（功能权限 + 数据权限按类型 + 角色管理 UI）   ← 第一刀，门禁
M6  动态表单 mini + 文件存储基建
M7  通知基建 + 定时任务调度
M8  人员 / 组织 / 档案
M9  在位状态 v2（基于人员管理，UX 一体）
M10 日报（周报预留）
M11 审批工作流（简单流 + 节点通知 + 联动在位）
vNext  多维表格 + 自动化流程、周报、Excel 导入、桌面客户端、外部 IM、内网交付强化
```

排序依据：**依赖关系 + 价值兑现**。权限/角色卡住一切排第一；动态表单+文件、通知+调度是被多个
业务模块共用的连接组织，先于业务模块；人员/在位/日报为核心业务；审批体量大且依赖通知，排其后。

#### 老 → 新映射

| 老（ADR-0002 / 旧蓝图） | 处置                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------- |
| 老 M5 审批 MVP          | 降级为新 **M11 审批工作流**，并改为“简单流”，移除“审批优先”定位                          |
| 老 M6 日/周报 MVP       | 拆为新 **M10 日报**（周报预留）                                                          |
| 老 M7 通知、实时、IM    | 拆分：**自研站内通知 + 调度**提前为新 **M7**；**实时网关 / OpenIM IM 移出本期**（vNext） |
| 老 M8 客户端与内网交付  | 移到 **vNext / 交付里程碑**；其中“服务镜像裁剪”等交付风险继续在 vNext 跟踪               |

> M1–M4 不变，`docs/verification-log.md` 中 M1–M4 记录继续有效。
>
> ADR-0003 所述「gateway 在 M7 起拆分为独立服务、退化为纯边缘网关」中的 M7 指**老 M7**；
> 该服务拆分随实时网关 / OpenIM 一并归 **vNext**，新 M7（通知 + 调度）**不**触发 gateway 拆分。

### 2. 战略原则：具体优先 + 前向兼容，不建“引擎”

每个能力先做“**具体、规则相对固定、但数据模型前向兼容**”的版本，等真实形态跑出来再在上层
统一抽象，避免过早通用化：

- **表单**：固定槽位 + 类型化字段，但存储用 `表单定义/字段定义/记录/记录值` 通用子集；填报快照存值。
- **通知**：少量内置触发点 + 接收人可配置，不做通用规则引擎。
- **审批**：可定义的简单串签流，不做条件分支/会签/动态节点。
- 三者的“可配置/自动化”统一收敛到 vNext 的多维表格自动化平台。

### 3. 本期不做即时通讯 / 不引入 OpenIM

- 本期用**自研轻量站内通知**（站内、已读未读、事件驱动、接收人可配、可选 SSE/轮询）。
- 通知抽象层保留干净接口，未来可叠加外部 IM 投递。
- **更正既有文档的事实错误**：OpenIM Server 许可证为 **Apache-2.0**，并非早期文档所述
  “AGPL，需合规评估”。（其客户端 SDK 许可证待真正集成时再单独确认。）

### 4. 范围固定项

- 单一企业、几百人；部门**本期两层**，但表结构按**树形**预留多层。
- 仅办公室电脑浏览器，**无移动端 / 无外网**。
- 数据权限采用**按数据类型分别授权**（模型 B）。

## 影响

正向：

- 先打通“权限/角色 → 共用基建 → 核心业务 → 审批”的依赖链，业务模块不返工。
- 把真正需要的基建（权限 UI、动态表单、通知、调度、文件存储）从模糊的“老 M7”里拆清。
- 砍掉本期不需要的 IM/实时重型集成，降低内网交付负担。

成本 / 风险：

- 文档面较大：需同步蓝图、进度板、doc-index，并清查旧文档中“审批优先 / 老 M5–M8 / OpenIM-AGPL”
  等过时表述（本 ADR 落地时一并处理）。
- “以人为中心 UX”与“模块/schema 隔离”存在张力，人员域的模块组织在 M8/M9 设计阶段定。

## 替代方案

- **维持老 M5 审批优先**：与实际优先级不符，且审批依赖尚未建好的通知与角色管理，会反向返工。
- **先建多维表格/自动化平台作为基建**：最大最险，价值兑现最晚，过早通用化，已否决（见决策 2）。
- **集成 OpenIM 同时获得聊天与通知**：运维与耦合代价过高，且其通知是 IM 域消息非业务通知，已否决。
- **里程碑用全新命名（P1/P2…）而非复用 M 系列**：已否决——老 M5–M8 从未实现、`verification-log` 仅含 M1–M4，复用 M 系列并清查旧引用即可；换前缀只会徒增团队适应成本。
