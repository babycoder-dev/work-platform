# ADR 0002: 基建优先的平台推进策略

## 状态

Accepted

## 背景

项目目标是建设企业内部轻量协作平台，短期覆盖审批、在位管理、日/周报，长期支持 IM、多维表格、日历事项等能力。

当前仓库已经具备基础工程结构、NestJS API、Web Shell、Platform Core 初版、权限 guard、DTO 校验、CI 与 Docker 构建验证。但 Platform Core 仍处于开发期内存存储状态，菜单、审计、数据库迁移、持久化 session、模块注册等基础能力尚未闭环。

如果现在直接进入业务模块完整开发，短期会产出页面和接口，但后续大概率在以下位置返工：

- 业务模块各自实现权限、菜单、审计。
- 内存 store 扩大后切换 PostgreSQL 成本升高。
- 业务模块直接互调或跨 schema join。
- IM、通知、实时能力侵入业务模块。
- Web 与桌面客户端行为不一致。

## 决策

项目采用“基建优先，业务验证跟进”的推进策略。

在进入审批、在位、日/周报完整业务开发前，优先完成以下平台基建：

- PostgreSQL schema 与迁移机制。
- Platform Core PostgreSQL repository。
- seed 与安装初始化流程。
- 密码 hash 与 session store。
- 模块 manifest、菜单、权限点注册。
- 审计日志。
- 领域事件/outbox 基础。
- Web Shell 登录、权限菜单、模块挂载。
- `@work/http-client` 与 `platform-sdk` 初版。

第一个业务模块仍选择在位管理，但它的角色是“验证平台基建”，不是绕开平台能力快速堆功能。

## 关键取舍

### 1. 不以远程微前端作为第一阶段目标

第一阶段目标是模块边界稳定，而不是远程加载。

理由：

- 当前团队规模和模块复杂度不需要立刻引入远程微前端运行时。
- 远程微前端会增加构建、部署、版本兼容复杂度。
- 本地模块化 + manifest 协议已经能验证大部分平台边界。

保留演进路径：

- IM、多维表格、日历等复杂模块未来可升级为远程微前端。
- Shell 只依赖模块 manifest，不依赖模块内部实现。

### 2. Platform Core 是所有业务模块的共享事实源

企业、部门、员工、账号、角色、权限、菜单、审计由 Platform Core 维护。

业务模块不得维护自己的员工、部门、角色、权限来源。

理由：

- 统一权限和数据范围是协作平台的核心。
- 审批、在位、汇报都依赖同一套组织与员工模型。
- 桌面客户端和 Web 客户端必须看到一致的数据权限。

### 3. OpenIM 作为 Provider，不作为平台账号中心

OpenIM 可以用于 IM 能力，但不能接管平台账号、组织、权限。

理由：

- 平台必须能在无 IM 或替换 IM 的情况下运行。
- 业务模块不能直接依赖 OpenIM。
- OpenIM 的许可证、SDK、部署和升级风险应被隔离在 `im-adapter-api`。

### 4. 数据库按 schema 隔离

单 PostgreSQL 实例，多 schema 隔离：

```text
platform.*
presence.*
approval.*
report.*
notification.*
integration.*
```

理由：

- 初期部署简单。
- 模块边界清晰。
- 未来可按模块拆库。

限制：

- 业务模块不得随意跨 schema 写入。
- 跨模块协作优先通过 API、事件、只读投影实现。

### 5. 桌面端不复制业务规则

Qt C/S 客户端只做原生交互和本地体验，不拥有独立业务规则。

理由：

- 避免 Web 与桌面端行为分叉。
- 简化权限、审计、数据范围一致性。
- 保持客户端轻量和可维护。

## 执行顺序

```text
M0 架构基线
M1 Platform Core 持久化
M2 权限、菜单、审计闭环
M3 Web Shell 可用基座
M4 在位管理 MVP
M5 审批 MVP
M6 日/周报 MVP
M7 通知、实时、IM
M8 客户端与内网交付
```

## 约束

- 所有新增 API 必须有 DTO 校验。
- 所有受保护 API 必须声明权限。
- 所有写操作必须考虑审计日志。
- 所有 schema 变更必须有迁移脚本。
- 所有模块必须有 contract。
- 每个提交必须通过 CI。
- Docker build 是交付门禁的一部分。

## 后果

正向影响：

- 后续业务模块复用统一权限、菜单、审计和组织模型。
- 能减少中期返工。
- 有利于内网部署和桌面客户端一致性。
- 有利于 AI 辅助开发时保持统一上下文。

成本：

- 前期业务功能产出速度会慢一些。
- M1/M2 需要投入较多平台工程工作。
- 需要维护更多架构文档和 ADR。

接受该成本。当前项目的主要风险不是业务模块写不出来，而是平台边界不稳导致后续无法持续扩展。
