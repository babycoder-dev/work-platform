# 产品需求规格（Product Requirements）

状态：Accepted ｜ 最后更新：2026-05

## 文档目的

本文档是本平台**业务产品需求的单一事实源**，回答“要什么、给谁用、边界在哪”。
它不写“怎么实现”——实现细节由各里程碑的 `docs/rfc/*.md` 和任务包 `docs/tasks/*.md` 承载。

本轮需求于 2026-05 与产品负责人通过结构化访谈对齐，替代了早期“审批优先”的口径。
重规划的决策背景与里程碑映射见 `docs/adr/0005-product-replan-roadmap.md`。

> **阅读约定（贯穿全文）**：每项能力都明确标注三种状态之一——
>
> - **【本期做】** 当前路线图（M5–M11）内交付。
> - **【预留】** 本期不做，但数据模型 / 接口 / 状态位要留好，并在此说明未来用途，避免留空白字段无人知晓。
> - **【vNext】** 远期愿景，本期不预留具体实现，仅记录方向。

## 1. 产品定位与目标用户

面向**单一企业内网**的轻量协作管理平台。当前阶段聚焦“**以人为中心的组织管理**”：
把人员档案、在位状态、日常工作上报、行政审批统一到一个权限可控的工作台里，
让管理者能清楚看到“**谁是谁、现在在不在、在忙什么、有什么待办**”。

- **规模**：几百人，单一公司。
- **部门层级**：【本期做】两层（公司为根，下挂部门；部门下不再展开科室/组）；【预留】部门表用树形结构（`parent_id`），未来支持多层嵌套，本期只是不展示更深层级。
- **运行环境**：办公室电脑浏览器。**无移动端、无外网访问需求**（出差状态在出发前于公司内提交）。

### 目标用户与种子角色

角色**可自定义**（可新建/删除、可配权限）。下列为出厂预置种子，不是写死枚举：

| 种子角色       | 典型职责                                                      |
| -------------- | ------------------------------------------------------------- |
| 普通员工       | 维护本人档案、登记本人在位状态、填报本人日报                  |
| 部门负责人     | 查看/管理本部门人员的档案、状态、日报                         |
| 公司负责人     | 全公司范围查看                                                |
| 公司负责人助理 | 范围接近公司负责人（多为查看/代办），但功能权限可与负责人不同 |
| 人力（HR）     | 全公司档案管理、定义员工信息表单；是否能看日报内容**可配置**  |
| 系统管理员     | 平台与角色/权限管理                                           |

> “日报管理员”不是角色，而是一项**功能权限**（自定义日报表单），可挂在助理或其他角色上。

## 2. 权限模型（平台命门）

权限由**两条正交的腿**组成，二者都挂在角色上：

### 2.1 功能权限（能做什么操作）

例：`自定义日报表单`、`自定义员工信息表单`、`发起审批`、`管理部门`、`管理角色`……
按钮、菜单、API 三处共用同一套权限点（沿用平台既有 `@RequirePermissions` 机制）。

### 2.2 数据权限（能看/操作谁的数据）—— **按数据类型分别授权**

采用**模型 B**：数据可见范围**不是每人一个统一范围**，而是**绑在“每一类数据”上**。
同一个人对不同数据类型可以有不同范围。

- **数据类型清单**（本期）：
  1. **个人信息 / 档案**（含**近况记录**——近况记录的可见/新增权限随档案数据权限走）
  2. **在位状态**
  3. **日报 / 周报**
  4. 系统 / 管理类（角色、权限、审计等，归系统管理员；**不参与按数据范围配置**，仅系统管理员持有，不与上述三类可配置数据并列）
- **范围枚举**（沿用平台 scope）：`本人 / 本部门 / 本部门及下级 / 全公司`。
  【预留】`自定义指定部门/人员`（per-person/custom）——本期不做；范围枚举保留该取值位，遇到时按 `本人` 安全降级并记录。

**配置示例**（正是访谈中确认的诉求）：

- HR：`档案=全公司` + `日报=无（可改为全公司）`
- 部门负责人：`档案=本部门` + `在位状态=本部门` + `日报=本部门`
- 公司负责人 / 助理：三类均 `全公司`
- 普通员工：三类均 `本人`

> **导出权限不单设**：能查看某范围的数据即可导出该范围（部门负责人导本部门、HR 导全部）。

## 3. UX 原则

- **充分参考飞书**（Lark）的信息架构与交互；具体页面在实现阶段我会先给设计简报/提示词，由产品侧用设计工具产出稿子确认后再开发。
- **以人为中心整合**：档案 / 在位状态 / 近况记录在 UX 上是**同一个“人”的不同切面**——一个人的页面能同时看到档案 + 当前状态 + 近况脉络；“看板”是“按状态筛人”的一个视图。**不做成互相割裂的模块。**
  > 技术上仍受平台模块/schema 隔离约束（在位当前是独立模块独立 schema）。这里存在“统一 UX vs 模块边界”的张力，**人员域如何组织（在位是否并入人员域、还是保持独立模块由 UX 聚合）留待 M8/M9 设计阶段定**，见 §8 待解决问题。
- **Web 与未来桌面端保持一致**：本期只做 Web，但交互与数据契约设计要让未来 Qt 桌面端能复刻同一体验（桌面端只走 gateway/SDK，不复制业务规则）。

## 4. 能力需求（逐条，按里程碑）

### 4.1 M5 权限与角色管理【本期做】

- 角色 CRUD（新建、编辑、删除、停用）。
- 给角色分配**功能权限**。
- 给角色分配**数据权限**（按 §2.2 数据类型 × 范围）。
- 用户—角色分配。
- 数据范围解析在既有 `PlatformScopeService` 基础上扩展为“**按数据类型返回范围**”。
- 这是后续所有模块的门禁，**排第一**。

### 4.2 M6 动态表单 mini + 文件存储【本期做】

**动态表单 mini**——“固定槽位 + 类型化字段”，不是任意表单生成器：

- 表单**槽位固定**（员工信息表单、每种在位状态的填报表单、日报表单），有权限者只能配置“该槽位有哪些字段”，不能凭空造任意新表单。
- **数据模型按多维表格前向兼容子集设计**：`表单定义 / 字段定义 / 记录 / 记录值`（通用结构，不为每个功能写死专用表），将来可平滑长成多维表格——是扩展不是重写。
- **字段类型**：单行文本、多行文本、数字、日期、单选、多选、**文件/图片上传**、**人员选择器**。
- **字段属性**：必填/选填、排序、字段说明。【本期不做】条件显示、联动、公式（vNext 由多维表格自动化承载）。
- **填报记录快照存值**：每条记录把**当时的字段标签 + 值**一起存下来（自描述），即使以后改表单，旧记录也不花屏，并为未来变更对比留好数据。
- 【本期不做】**完整表单定义版本化**——以快照替代；若未来要精确版本对比再补。

**文件存储基建**：

- 内网无 CDN，需平台级**文件存储服务**（本地磁盘 + 文件服务，或自建 MinIO，实现阶段定）。
- 服务于：档案照片、表单文件/图片字段。

### 4.3 M7 通知基建 + 定时任务调度【本期做】

**自研站内通知**：

- 站内通知，**已读/未读**。
- **事件驱动**：业务发领域事件 → 通知服务按规则生成站内通知。
- **接收人可配置**：每个触发点的接收人可配（不做通用 when-this-then-that 规则引擎，那是 vNext）。
- 本期触发点：① 日报截止前提醒未交者本人；② 日报交齐提醒负责人；③ 状态变更通知（默认部门负责人，**可配可加**公司负责人/HR/助理）；④ 个人信息被他人修改通知本人。
- **不通知**的明确项：给某人新增近况记录**不通知**本人。
- 通知接口本期做；其**外部 IM 投递为【预留】接口位**（留好扩展点，本期不实现）；真正接入外部 IM（如 OpenIM）属 **vNext**（见 §6）。

**定时任务调度基建**：

- 支持**可配置的日报截止时间**与定时检查（“在岗但未交 → 提醒”、“交齐 → 提醒负责人”）。

### 4.4 M8 人员 / 组织 / 档案【本期做】

- **部门管理**：树形结构（本期展示两层），增删改、人员归属。
- **账号创建**：HR/管理员后台创建 + 员工**首次登录改密 + 补全个人信息**（复用既有 `must_change_password`）。
  - 【预留】员工自助注册 + 审核：**数据表预留“注册/审核状态位”**（如 `registration_status: active|pending`），本期录入即 `active`；未来加注册审核只改写入 service 一处。
  - 【预留紧随其后】Excel 批量导入员工。
- **档案字段**：
  - **系统固定字段**（其他模块/平台依赖，不可删）：姓名、工号、部门、职位、手机、账号状态。
  - **HR 可自定义字段**（增删改类型，即“员工信息表单”，由 M6 动态表单承载）：出生日期、性别、婚姻状况、座机、入职日期……
- **个人信息编辑**：本人可改本人；HR 等按数据权限可改他人；**被他人修改 → 通知本人**（M7）。
- **建档审核**：【本期不做】录入即生效。所有“写档案”的操作**收口到一个 service**，未来要插“HR/副负责人审核”关只改一处。
- **近况记录**：事件脉络节点。字段=记录人（自动=当前用户）、记录时间、内容（纯文本）。支持**批量给多人添加**（用人员选择器选目标）。可见/新增权限随档案数据权限。

### 4.5 M9 在位状态 v2（基于人员管理，UX 一体）【本期做】

- **状态类型可自定义**：预置 在岗/出差/休假；HR/管理员可增减（“状态字典”，怕实际运行要细化）。
- **自助登记**：员工出差/休假等出发前自己提交状态变更。填报字段由 M6 动态表单配置（出差填地址/时间/事由等；**其他信息由档案自动补全**）。
- **看板**：按**数据权限**呈现组织范围内成员的当前状态。
  - “不在位” = 非在岗的所有人；【可后做】更细的状态筛选与**分部门展示**（属展示层，后端数据就绪后做）。
- **Excel 导出**：可选列；权限跟随查看权限（见 §2.2）。【可后做】具体导出体验。

### 4.6 M10 日报（周报预留）【本期做】

- **个人日报填报**：内容由**自定义板块**构成（如技术工作、文档工作……），板块/字段由 M6 动态表单配置（“自定义日报表单”功能权限）。
- **填报对象**：仅**在岗**人员需报（他们才在电脑前）。
- **汇总页**：管理者按数据权限看“今天哪些人在位 → 在位的哪些人已报/未报 → 各部门每人报了什么”。
- **未提交/交齐提醒**：依赖 M7 通知 + 调度（可配置截止时间）。
- **可见范围**（数据权限“日报”类）：部门负责人=本部门、公司负责人=全公司、普通员工=本人、HR 默认不看（**可配**）。
- 【本期不做】**日报变更对比（git-diff）**：先以快照存值留好数据，未来再做差异视图。
- 【预留】**周报**：用同一套机制（另一个表单槽位 + 按周聚合），本期不做。

### 4.7 M11 审批工作流（简单流 + 节点通知 + 联动在位）【本期做，排在核心业务之后】

- **审批与状态解耦**：状态自助上报；审批是独立流程（线下当面审批的线上化）。
- **可定义的简单审批流**：单级/多级**串签**；典型场景：请假、出差、物资申领。
- **节点通知**：审批流转到某节点 → 通知待办人（审批内置能力，依赖 M7）。
- **联动**：审批通过可触发其他能力（如请假批准 → 自动登记在位状态），**通过领域事件/公开 API 完成，审批模块不直接写 presence 表**。
- 【本期不做】条件分支、会签/或签、动态节点、表达式——这些归 vNext 自动化平台。

## 5. vNext（远期愿景，本期不预留具体实现）

- **多维表格 + 自动化流程**：把动态表单升级为通用 `表/字段/记录` 引擎，并提供“自动化流程”（事件→动作，含发通知、触发审批）。**表单、通知、审批三者最终在此统一收敛**。参考飞书多维表格 / apitable（注意 apitable 为 **AGPL-3.0** 且为重型多语言栈，仅借鉴交互与概念，不轻易引入其代码）。
- 桌面 Qt 客户端业务界面。
- 外部 IM（如 OpenIM）人对人聊天接入。
- 部门多层嵌套的完整展示与管理。

## 7. 关键技术约束

- 单一企业、单 PostgreSQL 实例、schema-per-module 隔离（`platform.* / presence.* / approval.* / report.* / notification.*`）。
- 内网部署、无公网 CDN、无外部 IdP。
- 后端 NestJS、前端 React、Drizzle ORM；沿用统一错误格式、审计、领域事件、`@RequirePermissions`、phantom-token 跨进程鉴权。
- 业务模块只能通过公开 API / 只读快照 / 领域事件协作，不跨 schema、不互调内部。
